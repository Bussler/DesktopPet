# Focus Mode - Feature Specification

## Problem Statement

The user wants a quiet way to alternate focused work and breaks without leaving the desktop pet app. A minimized timer should keep working, Hood should provide the focus-completion reminder, and breaks should visibly put him to sleep. During focused work, the user wants Windows notification suppression comparable to Windows Focus, without requiring administrator installation or execution.

## Solution

Add one Focus window accessible from Hood's menu and the system tray. It provides configurable focus and break durations, a remaining-time countdown, an always-on-top toggle, minimize, and timer controls. Initial defaults are 25 minutes of focus, 5 minutes of break, and always-on-top off. Preferences live only in memory; restarting the app starts idle with these defaults.

The repeating workflow is: manually Start focus; work while Hood behaves normally; reach zero and have Hood wave continuously; click Hood to restore Focus and acknowledge the reminder; manually Take break; have Hood display an uninterrupted sleep animation; reach zero and silently restore Focus with Break finished; manually Start focus again. Neither phase starts automatically. Pause/Resume and Stop are available for both timers; Skip break makes the next focus available without starting it. Closing Focus stops the cycle, while minimizing keeps it running. All timer reminders are silent.

Offer automatic Windows Do not disturb during running focus time, including when minimized, if a supported integration can work with normal user privileges. Pause, focus completion, breaks, Stop, and closing release only Hood's notification suppression. Preserve Windows Do not disturb that was already active. If integration is unavailable, inaccessible, or would require elevation, clearly offer Open Windows notification settings instead. This is Windows notification control, subject to Windows exceptions, rather than per-application presence or media controls.

## Implementation Decisions

- **Architecture and ownership:** Follow the accepted WPF frontend ADR. Keep the smallest cohesive focus-session/application behavior in the portable core, independent of Windows APIs, WPF, storage, and wall-clock waits. The Windows frontend owns the Focus window, both menu routes, pet input/presentation integration, and Windows notification access. Reuse existing application-owned window, appearance, elapsed-time, and command patterns. A small replaceable notification boundary is justified for actual Windows access and deterministic tests; avoid a general productivity framework.
- **Single window:** Both menu commands open or restore one app-owned Focus window and one timer cycle. Repeated opening does not reset time or create another controller. Opening alone never starts focus. Restoring a minimized window retains the timer state and effective always-on-top choice. Focus topmost is independent of overlay and Notes topmost behavior. Match existing theme/style resources and ordinary keyboard/accessibility conventions.
- **Duration contract:** Initial durations are 25 focus minutes and 5 break minutes. Inputs must be positive, finite, representable durations, with clear validation and no silent clamping to unrelated values. Reuse existing numeric-input conventions; exact practical bounds and layout are implementation details. Capture a duration when its phase starts. Editing future durations must not retroactively change a running or paused countdown; disabling those inputs during an active interval is acceptable. Remaining time is displayed as minutes and seconds, never below zero.
- **Phase contract:** The conceptual phases are Idle, Focus, Focus finished, Break, and Break finished; a running Focus or Break can be paused. These are observable states, not a mandate for a particular class hierarchy. Start focus from Idle or Break finished starts a full focus duration. Focus expiration enters Focus finished, releases suppression, and requests continuous waving. Take break from Focus finished starts a full break duration and replaces any wave with break sleep. Break expiration enters Break finished, retains break sleep, restores the window, and waits for Start focus. No elapsed-time overshoot starts the next phase or consumes its time. There is no fixed round count.
- **Acknowledgement and click precedence:** In Focus finished, a Hood click acknowledges a pending wave and restores/brings forward Focus without ordinary React or Notes activation. Acknowledgement stops waving but does not start the break; Hood returns to ordinary behavior while Take break remains available. If the window is already visible or opened from a menu, Take break works directly and clears the pending wave. During Break, a paused Break, and Break finished, a Hood click restores Focus without waking or toggling Notes. Outside these focus-specific situations, preserve existing click and Notes behavior. Preserve the existing distinction between a click and a drag.
- **Timer controls:** Pause freezes the remaining duration without restarting it. Resume continues that same duration. Pausing Focus releases Hood's suppression; resuming requests it again if enabled and available. A paused Break retains visual sleep. Skip break ends a running or paused Break immediately into Break finished, with no automatic focus start and no additional wave. Stop from an active, paused, or completed cycle returns to Idle, clears pending reminders and break sleep, releases Hood-owned notification control, and leaves the Focus window usable. Closing Focus performs the same cleanup and closes the window; minimize performs none of that cleanup. Timer preferences remain available in memory for the app run.
- **Visual pet behavior:** Focus itself does not change normal roaming, needs, naps, animations, or direct actions. Its completion wave loops using the selected pet's existing Wave animation until acknowledged, superseded by Take break, or cleared by Stop/close/reset. Break sleep uses the existing Sleep animation as a transient override, remains visibly at rest, and is not interrupted by ordinary clicks, feeding, spontaneous actions, or normal nap-completion animation. Pausing, finishing, or skipping a break does not release this override. Starting focus, Stop, close, app exit, or simple lifecycle reset releases it. Do not use an ordinary pet nap to implement the timer's break or award sleep-need recovery because the timer is on a break. Preserve underlying pet-care semantics, placement, and existing visibility; clearing an override resumes normal pet behavior rather than forcing an awake state or rewriting needs.
- **Countdown and alerts:** Drive the countdown with controlled active elapsed time using existing timing conventions; do not tie its progress to window rendering, visibility, pet animation settings, or Notes activity. A minimized or covered window continues counting. Focus expiration requests the pet reminder and waits for a click or direct window action; it does not automatically start a break. Break expiration explicitly restores and brings forward Focus with the exact status Break finished even if always-on-top is off. Do not leave the window permanently topmost merely to announce completion. No sound effects or audible timer alerts are added.
- **Notification option and availability:** The window provides an understandable option for automatic Windows Do not disturb when supported, plus accurate availability/status. When enabled, request suppression only for a running, unpaused Focus phase, irrespective of minimized state. Release it on Pause, focus expiration, entry to a break, Stop, close, reset, or orderly app exit. Resume and each manually started focus acquire it anew. Disabling the option releases Hood's control. A failure must not falsely show automatic protection as active or prevent timer operation.
- **Notification ownership:** Release only the control/session Hood actually acquired. Preserve pre-existing Windows Do not disturb, user settings, and focus sessions started elsewhere; do not use a global end-all-focus operation as ordinary cleanup. Breaks and waits allow notifications to the extent the user's other Windows settings permit them. If release fails, surface that state and the manual settings action instead of claiming restoration. Do not overwrite Windows priority-exception settings to promise broader suppression than Windows Focus provides.
- **Feasibility and fallback:** Attempt supported automatic Windows integration under normal user privileges. Starting and ending Windows Focus sessions currently require Microsoft Limited Access Feature permission/token; API and access availability must be checked and demonstrated for the app's existing distribution model. Do not equate a documented API with already granted access or assume administrator execution solves the access requirement. No elevation, privileged service, or administrator-only installation is part of this feature. If normal-user automatic control is unavailable, inaccessible, or unreliable, provide the approved Open Windows notification settings fallback with a clear explanation that control is manual. Do not ship a switch that pretends the fallback enables or restores notifications automatically.
- **Transient state and compatibility:** Focus durations, topmost choice, notification choice, countdown, phase, wave acknowledgement, and break overrides are in memory only. App restart begins idle with 25/5 durations and always-on-top off. Use a simple cycle reset/cleanup on computer sleep rather than restoring an interrupted timer on wake. No timer history, crash recovery, catch-up intervals, or dedicated recovery UI is required. Focus state does not extend configuration, pet-session, or Notes schemas and must not leak temporary wave/sleep overrides into saved pet state. Existing pet/configuration/Notes persistence and recovery remain governed by their existing contracts and the session-recovery ADR.
- **Compatibility and implementation discretion:** Respect existing sprite visibility, selected pet, sizing, appearance previews, Notes editing, and unrelated menu commands. Hidden sprites do not stop time or force the pet visible; the tray/window remain usable to complete the workflow. Exact layout, nonessential wording, duration input bounds, and internal type names are delegated to implementation within these contracts. Preserve the current architecture and keep changes lean. This specification does not require a new dependency, settings subsystem, animation asset family, or significant irreversible architecture decision.

## Testing Decisions

The user confirmed three boundaries in this conversation on 2026-10-14: deterministic application behavior with controlled elapsed time and simulated notification integration; focused WPF interaction tests; and separate native Windows acceptance against the packaged app. Test external state, commands, presentation, and observable side effects rather than duplicating private helpers. Do not wait through real focus periods or depend on live notification services for deterministic coverage.

- **Primary application seam:** Exercise the real focus-session/application commands, timer state, pet integration, and replaceable notification boundary. Cover defaults; valid/invalid durations; complete and partial intervals; zero and elapsed-time overshoot; continuous wave and acknowledgement; manual Take break; break completion; repeated manual rounds; Pause/Resume for both phases; Skip break without automatic focus; and Stop/close/reset from running, paused, and pending-completion states. Compare different elapsed-time slices where useful. Assert exact remaining time, no negative countdown, and no accidental advancement into a phase that requires a user action.
- **Pet behavior and compatibility:** Verify normal focus behavior against the existing session, wave precedence over ambient gestures, special-click precedence over React and Notes activation, unchanged Notes visibility/content, and uninterrupted break sleep through clicks, feeding, scheduled reactions, pauses, expiry, and skip. Confirm that a break does not invoke ordinary sleep recovery or persist a forced sleep/wave mode, and that lifecycle cleanup restores ordinary behavior. Preserve selected-pet/visibility settings and existing click-versus-drag behavior. Existing HoodSleepTests provide deterministic elapsed-time, nap, and needs prior art; NotesApplicationTests provide application-command and controlled-dependency patterns.
- **Notification contract at that seam:** Simulate available/unavailable access, successful/failed acquisition and release, a suppression option that is off, and Windows control that was already active or belongs to another owner. Verify requests only during running focus, retained protection when minimized, release on Pause/completion/break/Stop/close/reset/exit, re-acquisition on Resume/new focus, accurate failure/availability status, and the manual settings action without a false automatic-success state. Prior art includes the simulated external observations in MediaHeadphonePolicyTests and their integration with real pet presentation in HoodOverlayRenderingTests. Simulations establish Hood's decisions, not real Windows suppression.
- **Focused WPF seam:** Use the existing frontend interaction/rendering harness to check both command routes reuse one window/timer, phase and countdown text, validation and enabled controls, Pause/Resume/Stop/Skip actions, focused Hood-click routing, close versus minimize dispatch, topmost independence, and the break-completion request to restore the window. Follow relevant patterns in HoodOverlayRenderingTests, HoodDragTests, and Notes window interaction tests. Assertions on window state or a restore request do not establish real foreground activation, tray usability, or visible animation quality.
- **Native Windows acceptance:** Run an identified packaged executable as a normal user. Check both menu entry points, repeat-open behavior, minimize/restore, always-on-top on/off, a complete manual focus/break cycle, uninterrupted visible break sleep, wave acknowledgement without Notes toggling, silent Break finished restoration, keyboard access, and the current theme/style at supported display scaling. Verify actual Windows Do not disturb with representative Teams/Discord notifications under known Windows exception settings, including minimized focus, Pause, break, Stop/close, and pre-existing DND. Confirm the approved fallback on unavailable access and no administrator prompt. Record OS/API/access prerequisites and any verified limitation. Hearing no alert alone does not prove notification suppression.
- **Scope and evidence:** Keep sleep/restart coverage limited to the simple reset and cleanup; do not expand it into a recovery subsystem or exhaustive suspension matrix. For future implementation, run the standard Test workflow and the separate Build-AndPublish workflow for the candidate used in native acceptance. Report automated and manual results separately, tied to that candidate. For this documentation-only delivery, validate heading order, story form/numbering, requirement consistency, local links, and whitespace; an application build is not evidence that the specification is correct.

## Out of Scope

- Automatically starting either phase, a fixed round count, long-break schedules, or a separate Skip focus feature.
- Daily goals, history, statistics, streaks, task lists, Microsoft To Do, Spotify controls, accounts, synchronization, or cloud services.
- Persisting Focus preferences or progress, resuming old timers, offline catch-up, crash recovery, or complex sleep/hibernate handling.
- Audible alarms, sound selection, new animation artwork, or changing the pet's ordinary care/needs rules.
- Per-app Teams/Skype/Discord presence changes, app-specific account integrations, system audio muting, blocking applications, or suppressing alerts beyond Windows' supported notification rules.
- Administrator installation/execution, privileged helper services, or a guarantee that Microsoft will approve restricted API access.
- Changing pet/configuration/Notes storage schemas, rewriting Windows notification exception settings, ending someone else's focus session, or changing unrelated Notes and pet controls.
- Reimplementing the entire Windows Clock application, a general productivity platform, or non-Windows frontends.

## Further Notes

- This specification records the feature interview, the user's explicit confirmation of the copied behavior definition, and subsequent testing-seam approval in this chat. It is a proposed implementation contract, not a claim that the feature, automatic notification integration, tests, or native acceptance already exist.
- The latest confirmed choices govern: manual starts for both phases; normal pet behavior during focus; visual-only break sleep; silent window restoration only at break completion; continuous focus-completion waving until acknowledged or superseded; no persistent timer preferences; and suppression released on Pause. Stop/close/reset are explicit lifecycle exceptions to retaining break sleep until the next Start focus.
- Windows integration is the main feasibility dependency. Validate normal-user acquisition, ownership-aware release, and applicability to the existing app distribution before promising automatic suppression. The user approved the manual settings fallback if automatic integration cannot be provided under those constraints; that fallback does not block the timer feature. Record which mode is actually delivered. Microsoft documents restricted access for [starting a Focus session](https://learn.microsoft.com/en-us/uwp/api/windows.ui.shell.focussessionmanager.trystartfocussession?view=winrt-26100), [ending a session](https://learn.microsoft.com/en-us/uwp/api/windows.ui.shell.focussession.end?view=winrt-26100), and [Limited Access Features](https://learn.microsoft.com/en-us/uwp/api/windows.applicationmodel.limitedaccessfeatures?view=winrt-26100).
- Windows Do not disturb can permit alarms, reminders, calls, and configured priority apps; other notifications go to notification center. Therefore Break (notifications) means Hood releases its own control, not that it forcibly enables all notifications despite user settings. See [Windows notification behavior](https://support.microsoft.com/en-us/windows/experience/notifications-and-do-not-disturb-in-windows). The manual action opens the notification settings page using the documented ms-settings:notifications URI; see [launching Windows Settings](https://learn.microsoft.com/en-us/windows/apps/develop/launch/launch-settings).
- Retain the accepted portable-core/WPF split and existing durable-session recovery contract described in the project's architecture decisions. Temporary timer presentation must remain separate from durable pet sleep and reaction state. No new ADR or storage migration is needed for the agreed transient scope unless implementation uncovers a genuinely significant decision.
- Keep this specification in source-project documentation. Add concise user-facing instructions when the feature is implemented, distinguishing automatic versus manual notification control. Do not present future behavior as currently available in the app README or shipped user guides. Implementation tickets, code, packages, and external issue publication are separate work.
