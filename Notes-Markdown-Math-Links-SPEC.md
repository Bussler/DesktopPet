# Hood Notes — Markdown, Math, and Links Specification

## Problem Statement

Hood Notes already provides rich-text controls, lists, code, and tables, but users cannot write the agreed Markdown emphasis, heading, and divider syntax or view and edit mathematical formulas directly in their notes. Web references also need to become clickable links that open in the user's default browser. These additions must fit the existing editor and selected Hood appearance while preserving its bottom formatting toolbar and reliable local storage.

## Solution

Extend the current rich-text editor with immediate conversion of completed supported syntax from typing and paste. Add bold, italic, underline, strikethrough, six heading levels, horizontal dividers, inline and display mathematics, and labeled or plain web links. Equations render locally and reveal editable source when clicked; leaving the source renders them again. Add Create math block beside the existing editor context-menu actions, plus contextual link editing and removal.

Use the current Hood UI style, Notes brightness theme, individual note color, and Notes text-size setting for the new content. Preserve existing controls, code, tables, lists, checklist behavior, editing history, and saved notes. This document specifies the accepted extension; the existing Notes and UI Styles specifications continue to govern unrelated behavior.

## Implementation Decisions

- **Boundaries and simplicity:** Keep the portable Core and Windows frontend split. Core owns the semantic Notes document, validation, transformation contracts, history, and local persistence. Windows owns rich-text adaptation, native focus/selection, equation presentation, clipboard integration, context menus, and default-browser invocation. Reuse current document transformations, application callbacks, history, table/list adapters, and appearance resources. Add only the smallest concrete math-rendering and browser-launch boundaries; do not introduce a generic plugin, parser framework, or second editor.
- **Supported syntax:** The required inline syntax is `**text**` for bold, `*text*` for italic, `__text__` for underline, and `~~text~~` for strikethrough. Double underscores deliberately mean underline. Use `# ` through `###### ` at the start of a note-body paragraph for H1–H6. A standalone `---` becomes a horizontal divider when its line is completed. Math uses `$expression$` and `$$expression$$`. Links use `[label](https://example.com)` or complete plain HTTP/HTTPS URLs. This is the agreed subset, not a promise of general Markdown or arbitrary HTML support; existing supported table-cell formatting remains compatible.
- **Conversion lifecycle:** Convert newly completed inline markers immediately after the native edit transaction finishes, without an explicit render command. A complete pasted fragment receives equivalent parsing, including a final standalone divider without a trailing newline. Live heading conversion occurs when its line-start prefix and following space are completed. Live divider conversion occurs when Enter completes the standalone line. Incomplete, empty, escaped, and unsupported syntax remains editable literal text. Support properly nested combinations of the four text styles. Preserve existing manual styles outside and inside the affected text.
- **Literal text and parse precedence:** Restrict live recognition to newly entered or newly completed syntax rather than reprocessing an entire saved note on unrelated edits. Loading, restyling, undo, and internal rich-content round trips must not reinterpret literal text. Protect inline code, fenced-code bodies including unfinished fences, math source, escaped characters, and existing semantic content before applying ordinary text syntax. Recognize a complete table and its separator rows without converting them into dividers. Display delimiters take precedence over inline dollars; a source span cannot become both math and a text style or link.
- **Editing and offsets:** Use the existing normalized text/selection contract consistently across conversion, rendered content, source editing, clipboard, and history. Map caret and selection across removed syntax instead of jumping to the end or selecting unrelated content. Preserve scroll position where the document geometry permits. Heading completion returns subsequent Enter-created paragraphs to ordinary text. Dividers and rendered equations remain selectable/deletable content with reachable text positions around them. Preserve note-local undo/redo; undo can recover pre-conversion input and redo can recover its semantic result without an immediate re-conversion loop. Persisted undo stacks across restart are not required.
- **Context scope:** Inline styles, inline equations, and links work in ordinary note text, headings, bullets, numbered lists, checklists, and table cells. Headings, dividers, and display math are standalone note-body content, not cell block types. The new block syntax must not destroy a list or table when entered in an unsupported position; retain it as literal text there. Existing list, checklist-completion, table alignment/structure, code, and navigation behavior remains intact. Completion appearance must preserve manual styles, equation source, and link destinations.
- **Math contract:** Store each expression's editable LaTeX source and inline-versus-display identity independently of its rendered output. Preserve source whitespace and line breaks; do not persist an image as the only representation. Accept same-line display source and multiline source between standalone `$$` delimiter lines. Inline math stays within its text paragraph; complete standalone display input becomes a note-body block and preserves neighboring text. An incomplete block does not trigger formatting of its source as prose.
- **Math coverage and engine:** Support fractions, roots, powers, subscripts, Greek letters, common mathematical operators and symbols, sums and integrals with bounds, matrices, and aligned equations. Rendering must work offline with required fonts/assets packaged locally. No full LaTeX document compilation, user packages, file access, command execution, or custom macro environment is required. Select the smallest maintained rendering integration that covers the confirmed notation and works with the current Windows frontend. Its package, font/assets, redistribution terms, and practical rendering limits must be documented when selected; selection is an implementation detail, not a new architectural framework.
- **Equation source interaction:** A normal click on a rendered equation reveals its source at that position and focuses source editing. This is in-place editing, not a separate equation window or source/preview mode. Leaving that source commits its current text and renders valid math again. Enter in a display-source editor inserts a source line break; leaving through keyboard navigation must also be possible without replacing established editor shortcuts. Invalid or unsupported source remains editable with a small local error indication and no blocking popup. Empty menu-created blocks retain a discoverable editable placeholder when unfocused. Correcting a formula clears its error and produces rendered content. Editing state and error decoration are presentation state; source is saved even while unfinished.
- **Create math block:** Add the action to the note editor context menu alongside Create table, retaining existing commands and styling. With no selection in ordinary note-body text, insert an empty display block at the caret, splitting surrounding prose as needed, and focus its source. With selected note-body text, replace exactly that text with a display block whose source preserves the selected characters and line breaks. Do not implicitly strip preexisting dollar delimiters or rewrite the expression. A table or code context follows the existing Create table convention by placing new standalone content adjacent to the containing structure; do not place display math inside a cell or flatten structural content. An incompatible selection containing table/other structural objects must retain accepted content and decline destructive wrapping through existing recoverable editor feedback.
- **Links and recognition:** Persist the visible label and validated absolute destination as semantic link information rather than relying on colored text. Only HTTP and HTTPS destinations become active, including case-insensitive scheme recognition. Markdown links convert after their closing syntax is complete. Plain URLs convert after a complete paste, whitespace, Enter, or leaving that text. Keep surrounding sentence punctuation outside the destination while retaining valid balanced address punctuation, query strings, and fragments. Unsupported schemes, malformed destinations, or incomplete input remain literal; Edit link validates the destination before committing.
- **Link interaction:** A normal click activates the link and requests its destination in a new tab of the Windows default browser. No Ctrl-click requirement, embedded browser, configurable browser selector, or fallback to a hardcoded browser. Loading, parsing, pasting, restoring, and restyling never activate a destination. Provide right-click Edit link and Remove link; editing can change label/destination or be canceled, and removal retains label text and its ordinary formatting. Provide keyboard access to activation and context actions without changing existing note shortcuts. Handle a launch failure through recoverable editor feedback without changing the saved document or crashing Hood.
- **Browser boundary:** Keep validated destination handling separate from native launch invocation so editor tests can observe requests without launching an external app. Validate both saved/edited link content and the destination submitted for activation. The acceptance target is a new tab in the actual Windows default browser; a process-start success or submitted URI alone does not prove tab behavior. Confirm this through native acceptance and report any browser-specific limitation explicitly instead of treating automated request checks as proof.
- **Appearance:** Extend the central appearance/content resources for headings, dividers, equations, links, source placeholders, error indicators, and interaction states. Follow the currently effective UI style, including its preview/restore lifecycle, rather than only its last saved identifier. Retain Sticky Notes, Minimal, Soft, Studio, Light/Dark/System, and the five existing note colors. Derive heading and equation sizing from the Notes text-size setting; H1–H6 remain a clear ordered hierarchy. Math may use a notation-appropriate font while taking size, foreground, and surrounding presentation from the current style. Exact ratios, spacing, line thickness, error appearance, and overflow treatment are implementation choices subject to readability and native acceptance.
- **Live refresh and layout:** Style, theme, note-color, and text-size changes update existing new content without rewriting semantic data or terminating a source edit. Preserve caret, selection, scroll position where meaningful, undo/redo, and window membership/geometry. Retain the bottom toolbar's current contents, position, focus-based visibility, and reserved space; retain the existing idle-scrollbar layout and right-edge interaction. Long formulas and URLs must remain reachable and readable at supported minimum note sizes and common display scaling. Do not silently truncate content or shrink mathematics into unreadability to make it fit.
- **Clipboard:** Preserve existing ordinary rich-text/list clipboard behavior and the existing Copy table as Markdown action. Plain text for a selected rendered equation contains its source wrapped in `$` or `$$` according to its type; mixed selections keep prose, equations, and block order. Copying a partial selection while editing source copies the selected source characters normally. Plain-text copying of a link keeps its visible label (a plain-URL link's label is its URL); supported rich clipboard data retains its destination. Extend the existing table Markdown round trip to retain supported cell emphasis, inline math, and link destinations, escaping pipes, delimiters, and literal marker text as needed. Pasting rich semantic content restores that content rather than converting already literal text a second time. No whole-note Markdown copy/export action is added.
- **Saved contract and compatibility:** Evolve the versioned Notes schema explicitly to represent heading levels, dividers, equation source/type, and link labels/destinations. The current loader accepts schemas 1–3 and rejects unknown fields; extend its migration and validation coherently, retaining support for earlier valid data. Exact field layout and new version number are implementation choices. Earlier notes retain their literal characters, styles, list/checklist state, code, tables, names, colors, placement, visibility, and Trash membership. Do not run source parsing as a migration or load step. Unsupported future or damaged data follows acknowledged recovery rather than silent field dropping/reset. Do not claim backward reading by older executables.
- **Data integrity and failures:** Semantic copy, slicing, equality, history, validation, plain-text projection, search/previews, and serialization must account for every new content type. Preserve the existing Notes character/store limits, accounting for formula source and destination data rather than only rendered labels; reject over-limit edits without truncation. Continue safe replacement writes, retained editable in-memory content on save failure, retry, and source-preserving recovery. Malformed persisted structure is a validation/recovery failure; syntactically invalid but structurally valid formula source is normal saved editable content. Rendering failure must not erase source. Flush source edits at existing close/hide/exit boundaries.
- **Documentation and delivery:** Update the user-facing Notes guide during implementation with syntax, nonstandard underline convention, equation editing, context actions, supported destinations, clipboard behavior, and any documented renderer limits. Keep this specification and internal evidence separate from the existing user-facing published package allowlist. Do not alter repository visibility or licensing as part of the extension.

## Testing Decisions

- **Confirmed seam plan:** The user confirmed automated Notes editor actions and real save/reload, a controlled browser-launch boundary, and manual Windows acceptance. The primary automated boundary is the existing WPF Notes editor interaction harness connected to Notes application callbacks. Drive typing, paste, selection, context actions, equation-source entry/exit, clipboard, undo/redo, and appearance changes; assert the resulting semantic document and observable native control behavior.
- **Good tests:** Use user-level actions and supported production contracts. Observe accepted text, styles, heading levels, block identities, exact equation source, rendered-versus-source state, link labels/destinations, selected ranges, clipboard data, history outcomes, save/reload, and recoverable errors. Prefer the highest boundary that exposes the result; add focused portable contract tests only for transformation/validation/migration cases that need deterministic edge coverage. Do not depend on private helper layout, exact object hierarchies, timers, real delays, or fake renderer success as proof of mathematical support.
- **Prior art:** Reuse the patterns in NotesApplicationTests, NoteListFormattingTests, NoteCodeFormattingTests, NoteTableTests, NoteInteractionTests, NoteCodeInteractionTests, NoteTableInteractionTests, and NoteContentContrastTests. Existing application tests cover real local-store round trips, failed-save retry, search, Trash, and undo/redo. Windows interaction tests drive actual rich-text controls and native key events and inspect saved callbacks; contrast tests refresh existing content across styles, themes, and colors.
- **Syntax and parser regressions:** Exercise each required inline marker, combined/nested emphasis, escaping, unmatched/empty input, multiple spans, typed/pasted equivalence, heading prefix boundaries and H1–H6, divider completion, code/fence exclusion, table-separator precedence, ordinary punctuation, and edits adjacent to existing formatted spans. Verify normalized line-break and selection mapping, undo without re-conversion, and no unrelated conversion on load, restyle, history replay, or later edits.
- **Math integration:** Exercise the actual chosen renderer through the editor with representative fractions, roots, scripts, Greek symbols, sums/integrals, matrices, and aligned equations. Cover both delimiter types, same-line/multiline blocks, source click/edit/leave, empty menu-created blocks, selected multiline source, neighboring text, invalid/unsupported input, escaped dollars, code/math-source literal treatment, and multiple independent equations. Assert valid rendering and preserved source/placement rather than checking only parser acceptance; renderer failures retain source and do not escape the UI boundary.
- **Menus, contexts, history, and clipboard:** Check both Create math block paths, selection replacement, non-destructive unsupported structural selections, source focus, link Edit/Remove/cancel, ordinary cut/copy/paste, delimited equation text, rich content, and table Markdown round trips including literal markers, equation pipes, URL punctuation, and list/checklist content. Verify existing toolbar states/actions, current shortcuts, Create table, table navigation, list continuation, code entry/exit, and checklist completion behavior with mixed new content.
- **Link launch contract:** Supply a controlled launcher at the Windows boundary. Activate typed/pasted labeled and plain links and assert exactly one request for the validated HTTP/HTTPS destination. Verify no requests during conversion/load/restyle, malformed or forbidden schemes, click versus source editing, canceled edits, removal, and launch failure feedback. Automated tests must never open a real browser.
- **Appearance:** Extend existing contrast/resource tests across all UI styles, Light/Dark, representative System resolution, the five note colors, and Notes text sizes. ## Out of Scope

- A full Markdown engine, extra inline aliases, general HTML, blockquotes, images, embedded media, or additional Markdown features beyond the agreed subset and current supported code/list/table behavior.
- A separate Markdown editor, split preview, equation dialog, a redesigned or expanded bottom formatting toolbar, or new global appearance settings.
- Full LaTeX documents, user-loaded packages/custom macros, external execution, remote rendering services, or a promise to support every LaTeX command.
- Headings, dividers, and display-math blocks inside table cells; restructuring cells or code to accommodate body-block syntax.
- Active email, local-file, custom-scheme, or relative-destination links; an embedded browser or browser selector.
- Whole-note Markdown export/copy, new import/export formats, synchronization, cloud storage, accounts, or persisted edit-history stacks.
- Reinterpretation of existing saved literal source on upgrade, new note-management/lifecycle features, repository licensing/visibility changes, or unrelated Hood behavior changes.
